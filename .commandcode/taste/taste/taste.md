# Taste
- Prefers a single source of truth for configuration/visibility over duplicated legacy settings; when a dedicated subsystem already manages a concern (Homepage Layout Builder for visibility, the theming system for themes/layouts/colors), favors deleting the redundant controls from the general settings page rather than keeping both — including removing their guards, casts, dead columns/queries, and orphaned CSS/JS. Confidence: 0.9
- Prefers grouping related admin settings fields into the logical section they belong to (e.g. moving logos/image pickers into Basic Information) instead of leaving them in a separate card. Confidence: 0.7
- When deduplicating/grouping records, prefers the non-destructive option that keeps every underlying attempt (aggregated inside the single grouped row) over overwriting or deleting older data — wants nothing lost, especially when the repeats are themselves a useful signal (e.g. one visitor trying several phone numbers). Confidence: 0.65
- Requests git commits by short-hand naming only the feature (e.g. `git commit phone block`) and expects the agent to work out the exact file set: stage only that feature's changes, deliberately leave out unrelated in-progress work and files that mix multiple features (flagging them and offering to commit them separately), and keep each commit a coherent, self-contained unit. Confidence: 0.7
- Wants commit messages that carry a real rationale in the body: why non-obvious files are included (e.g. the test-harness fix shipped alongside the test it makes safe) and what was intentionally left out. Confidence: 0.5
- Treats the agent's todo list as the contract of outstanding work and expects a terse "complete todo" to actually implement the remaining planned items end-to-end, not merely re-mark or audit them. Confidence: 0.6
- Communicates in terse, informal, typo-tolerant messages and often specifies a task by simply pasting the target URL (e.g. `http://127.0.0.1:8080/admin/settings/edit`); expects the agent to inspect the page/code and infer the details rather than asking for a full spec. Confidence: 0.8
- For larger/ambiguous features, wants a scoping or change-impact estimate first — what would need to change, roughly how much, and the key decisions that drive the size — before implementation begins. Confidence: 0.5
- For auto-create/sync features, wants the non-destructive "only fill the gaps" behaviour: create solely the records that are missing and leave any existing records (including user-renamed or inactive ones) untouched, keyed by an explicit/stable identifier rather than auto-increment. Confidence: 0.6
- For anti-abuse/fraud controls, prefers hard enforcement on customer-facing channels (storefront checkout, mobile API) while not blocking staff operations: the POS/admin surface shows a warning but staff can still override and complete the action. Confidence: 0.5
- Prefers missing critical configuration to be self-healed automatically rather than requiring a manual step (e.g. "add it to auto generate system" for APP_KEY), and wants such repairs wired into the app's own install/update mechanism so they ship and re-apply — not just documented as a manual command to run. Confidence: 0.6
- Prefers a single, consistent responsive/device-tier model across the app rather than feature-specific breakpoint sets: when given the choice, opted to extend the same device tiers (desktop/laptop/tablet/phone) to drive both layout column widths and per-device visibility toggles end to end. Confidence: 0.55
